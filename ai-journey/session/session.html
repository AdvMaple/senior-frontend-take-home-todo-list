This is **JTL’s Senior Frontend Engineer take-home assignment**. The frontend folder currently contains instructions only—there is no starter application or implementation to review.

## What you need to build

A small app with four capabilities:

| Feature | Required behavior |
|---|---|
| Create user | Form accepting a username |
| User details | View a user by ID |
| Create todo | Form accepting a title and assignee user ID |
| User’s todos | List todos assigned to a given user |

## Mandatory stack

- **React + TypeScript + Vite**
- **Turborepo** monorepo
- **TanStack Router** for routing
- **TanStack Query** for fetching, caching, and mutations
- **Jotai** for at least one cross-cutting UI concern
- **TailwindCSS**
- Form validation, accessible forms, loading states, and error handling

A mock or in-memory API is expected. No real backend is necessary.

## Main architectural constraint

The suggested structure is:

```text
apps/web          Routing, pages, application composition
packages/users    User components, hooks, API calls, types
packages/todos    Todo components, hooks, API calls, types
packages/shared   Shared infrastructure, utilities, state
```

**`users` and `todos` must not import each other.** The app composes the features; shared concerns belong in `shared`.

For example, `apps/web` can obtain user information and pass an assignee ID into a todo component without introducing a dependency between the feature packages.

## Most important behavior: optimistic todo creation

The assignment explicitly highlights this:

1. Submit a todo.
2. Show it in the relevant user’s list immediately, before the API responds.
3. Reconcile it with the server result on success.
4. Roll back correctly on failure and show a meaningful error.

Pay particular attention to **user-specific query keys**, switching users while a request is pending, and overlapping submissions. These are useful follow-up interview topics.

## Required deliverables

- Source code.
- A short architectural README, approximately half a page.
- Local installation and run instructions.
- Short reflections on:
  - Performance considerations.
  - Production testing strategy.
- An **`ai-journey/` folder** containing:
  - Your plan.
  - Key prompts.
  - Tools, models, skills, and MCP servers used.
  - Your judgment: what you checked, rejected, or changed.

**The AI journey is evaluated on par with the code**, so it should not be left until the end.

## Scope and priorities

The expected time box is **2–4 hours**. Prioritize:

1. Clear package boundaries and separation of concerns.
2. Correct optimistic creation and rollback.
3. Deliberate routing, query caching, and Jotai usage.
4. Accessible forms with helpful validation.
5. Concise documentation explaining real trade-offs.

Do not spend time on authentication, CI/CD, a real backend, elaborate design, or exhaustive test coverage. Implemented tests are not required, but a focused test for optimistic rollback would be useful evidence.

**Submission:** create your own repository or provide a ZIP. Do **not** open a PR against the original assignment repository.

what the root cause of the page position reset?
Assistant 2026-11-08T17:30:14.671Z
The reset was caused by **TanStack Router’s default navigation behavior**.

When the page size, page number, filter, or sort changed, the app called:

```ts
router.navigate({ to: Route.fullPath, search: next });
```

By default, that navigation resets the scroll position to the top of the document. Because pagination is below the list, this made it look like changing pagination sent the user away from the control they had just used.

The fix adds:

```ts
resetScroll: false
```

So the search-parameter URL still updates, but the router preserves the current viewport position.
